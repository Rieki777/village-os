**The asymmetry that defines the work:** game-amora has the better *registry*
(typed, bounded, delta-only, admin-editable — but invisible to members);
regen-civics has the better *surface* (a public GameMechanics page with
sliders, diff view, shareable state, and a "copy proposed changes" generator —
but its registry is a loose key/value table with fallbacks). The initiative is
each system adopting the other's strength, plus the Hypha loop on top.

## The three rings (proposed vocabulary for every value below)

- **Ring 0 — Constitutional.** Never tunable by anyone: conservation, one
  gate, fiat-in-only, witness rules' EXISTENCE. Enforced in code, listed
  publicly on the mechanics page as "the laws", not sliders.
- **Ring 1 — Founder-config.** Tunable, but not by open governance: legal
  posture (trading card version, legal acks), infrastructure (RPC URLs,
  secrets), abuse guards. Admin section only.
- **Ring 2 — Open mechanics.** The community-governable dials: budgets,
  pools, caps, multipliers, thresholds, cadences. These appear on the public
  Game Mechanics page and are the domain of the Hypha proposal loop.

Every "already-mechanic" and "make-variable" row below is implicitly Ring 2
unless marked founder-config (Ring 1). The registry's min/max bounds stay
Ring 0 — governance can move a value WITHIN its bounds, never the bounds.

# Part A — game-amora

## A1. The registered variable registry — 77 mechanics, admin-editable today, **no public page**

> Exact count: 77 VariableDefs in shared/gameVariables.ts (verified by grep on key lines), across 21 categories: Gratitude (6), Ledger (1), Quests (5), Governance (3), Tokens (4), Hypha (5), Tools (2), Accounts & sessions (2), Abuse guards (5), Data lifecycle (2), Village map (7), Forum (1), Feed (5), Stays (9), Exchange (5), Library (8), Payments (3), Village (1), Health (1), Badges (1), Platform (1). All are admin-editable today via one endpoint; none are publicly visible. STORAGE CONTRACT (server/lib/variables.ts): the game_variables table stores DELTAS ONLY — setVariable writes an override row only when the value differs from the platform default, and setting a value back to its default DELETES the row, so un-opinionated villages inherit future platform defaults on upgrade (explicitly contrasted in-file with regen-civics' seed-every-row approach, which needs a migration to change a default). Overrides are cached in memory, loaded fail-loud at boot (loadVariables), read synchronously on hot paths; the single async write lives in the admin endpoint. value_type is always written as literal 'text' regardless of def.type — the def, not the row, is the type authority. READY-MADE API FOR THE PUBLIC PAGE: allVariables() (variables.ts:61-73) already returns every def with value, parsed value, and isDefault flag — a public Game Mechanics page can be a filtered projection of exactly this, but it MUST filter: tokens.base_rpc_url, hypha.link_* overrides, and the five abuse.* rate limits are operational/security knobs whose public display is either noise or mildly attacker-useful; retention.* and auth.session_days belong on a privacy page more than a game page. Values are stored as strings and parsed by type (integer/decimal/percentage/boolean/choice/text); text validation includes 255-char cap, 0x-address regex for *_address keys, and https-only (loopback-exempt) for *_url keys. Two knobs are declared-ahead-of-enforcement policy contracts (stay.credit_expiry_days, library.dispute_deadline_days auto-settle) — the public page should not present them as enforced. platform.feedback_relay is an integer 0/1 masquerading as a boolean. current_value in findings = the platform default; live effective values require reading the game_variables table (deltas) and were not inspected (READ-ONLY audit, no DB access).

# Part E — Open questions (answer before building)

1. **Ring assignment authority.** The three-ring model needs an owner per
   variable. Is the ring a PLATFORM decision (fixed in code per variable), or
   does each village's founder choose which Ring-2 dials their community may
   govern (a per-variable "governable" flag the founder sets)? Recommendation:
   platform sets a ceiling (some things can never be Ring 2), founder opts
   variables into open governance underneath it.
2. **Which chain and which DAO product, exactly?** The working bridge verifies
   **Base (EVM) via Alchemy**. But regen-civics docs also reference EOSIO-era
   Hypha ($RCivics on EOSIO in BLOCKCHAIN_INTEGRATIONS.md). Is every village
   DHO — Amora's included — on app.hypha.earth on Base, with the same
   ProposalCreated/ProposalExecuted event shapes the webhook already parses?
   If any target DHO is still EOSIO-Hypha, the verification layer is a second
   implementation, not a port.
3. **Who runs the listener?** Two architectures: (a) every fork registers its
   own Alchemy webhook (sovereign, but every founder needs an Alchemy account
   and a signing key — real onboarding friction), or (b) the ReGen hub runs
   ONE listener service for all forks and forwards verified outcomes to each
   village over a signed callback (fits the existing feedback-hub
   "queue-and-forget, hub is a listener" pattern; villages stay servable when
   the hub is down because apply-on-callback is idempotent and re-sendable).
   Recommendation: (b), with (a) as an escape hatch. Which do you want?
4. **Who may propose?** Any signed-in member? A stage floor? The existing
   `governance.hypha_threshold` variable (earned recognition to qualify)?
   And is proposing rate-limited? Recommendation: reuse
   `governance.hypha_threshold` + a per-member weekly cap, both themselves
   Ring 2.
5. **Apply timing.** Instant-on-verification, or at the next cycle boundary?
   Mid-cycle changes to pool/budget variables have real hazards (the sticky
   cycle-split work exists precisely because mid-flight basis changes corrupt
   settlements). Recommendation: economic variables apply at next cycle
   close; non-economic (copy, toggles) apply instantly. Confirm.
6. **Does passage on Hypha bind automatically, or does a founder ratify?**
   Auto-apply is the stated goal; is there an emergency brake (founder can
   freeze auto-apply, loudly, with an audit trail)? Recommendation: yes —
   a Ring-1 "governance.auto_apply_enabled" kill switch.
7. **Batch proposals.** One proposal = one variable change, or a change-set
   (several dials moved together, e.g. a whole harvest-split rebalance that
   must sum to 100)? The harvest split literally cannot be changed one key at
   a time without passing through invalid states. Recommendation: change-SETS
   with an atomic apply. Confirm.
8. **Identity linking.** For "return and say it passed" attribution: is the
   proposer's Hypha/wallet identity linked to their game account (game-amora
   already has wallet verification via signed nonce)? Without it anyone can
   claim anyone's passed proposal. Require verified wallet for one-click
   bridge, allow copy-paste flow without?
9. **What do custom-game forks inherit?** Ring assignments, the mechanics
   page, and the bridge presumably ship with the platform; does the HUB also
   want a directory view ("this village's constitution") via the
   /api/platform/info handshake?
10. **Scope check on "all users of the tool".** The public page shows values
    to EVERYONE including anonymous visitors (like regen-civics)? Or
    members-only? Anonymous read is the regen precedent and the transparency
    point — confirm, since some variables (abuse-guard caps) arguably help
    attackers; those are Ring 1 and would stay OFF the page.

# Part F — Ways to improve the overall idea

1. **Publish the constitution, not just the dials.** The page's most radical
   feature is the Ring 0 list — the things NO vote can change. That is what
   makes the tunable list credible to outsiders and funders.
2. **Change-sets with invariant checks, not single-key edits** — e.g. the
   harvest split rows must sum to 100; a proposal is validated as a WHOLE
   against per-set constraints at creation time, not apply time.
3. **A mechanics ledger, mirror of the token ledger.** Every applied change:
   who proposed, in-game sensing results, Hypha proposal id, tx hash,
   basescan link, when applied, previous value. Renders as a public
   "Amendment history" on the page. Delta-only storage means history is
   currently THROWN AWAY on revert-to-default — the ledger fixes that.
4. **In-game sensing BEFORE the chain.** You already have
   `governance.sensing_days` and voice weighting in game-amora, and forum
   integration in regen-civics: let a proposal collect in-game
   support/perspectives first, and only offer the "take it to Hypha" button
   once it clears a visible threshold. Cuts chain noise, creates deliberation.
5. **Simulator-first proposing (regen already half-has this).** The regen
   page's slider+diff pattern generalizes: the proposal IS the simulator
   state. For game-amora, wire live figures (current pool, member count,
   recognition distribution) so movers see projected impact ("pool 500→800 ≈
   +2.1 per active member at current breadth") before proposing.
6. **Bounds are the safety envelope — publish them.** min/max in the registry
   are Ring 0. A proposal outside bounds is unproposable at form time, not
   rejected at apply time. (game-amora's registry already has bounds;
   regen-civics's mostly doesn't — porting the typed registry there is part
   of this work.)
7. **Cooldowns per variable.** A dial that moved last cycle can't move again
   for N cycles (N itself Ring 2). Prevents thrash and vote-fatigue attacks.
8. **Expiring experiments.** Let a proposal carry an optional sunset: "raise
   pool to 1500 for 3 cycles, then auto-revert unless re-passed." Communities
   experiment safely; the mechanics ledger records the experiment.
9. **One listener service at the hub** (see question 3): forks get
   verification without Alchemy accounts, and the hub gets an ecosystem-wide
   view of governance activity — the beginnings of the village directory.
10. **The proposal carries its own receipt path.** Put the bridgeKey marker in
    the Hypha proposal title (regen's existing `[rc:key]` pattern) so
    verification is deterministic; "return to say it passed" becomes a
    fallback for copy-paste proposals, with on-chain check before apply.
11. **Templates/presets for forks.** A custom game picks a starting
    constitution ("tight-knit village", "open network", "high-trust co-op") —
    a named bundle of Ring-2 defaults; the blueprint system in regen-civics
    (customGameBlueprint) is the natural home.
12. **Per-variable provenance on the page.** Show default vs current, who
    changed it last and under which proposal — every number becomes a story,
    which is exactly the pedagogical point of a public mechanics page.
13. **Don't move module-config mechanics into the registry blindly** (A3):
    structural JSON (forum categories) isn't a dial. Instead give the public
    page pluggable "sections" that read each plane read-only, and only
    promote to the registry what governance should MOVE.
14. **Test the loop against a Hypha sandbox DHO before shipping** — the QA
    harness pattern (scratch DB + smoke) extends naturally: a fake Alchemy
    payload injector + a sandbox DHO gives an end-to-end governance drill.
