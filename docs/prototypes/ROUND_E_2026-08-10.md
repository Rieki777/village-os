## How to verify this round, and the way to get it wrong

Round E's ARTIFACT and its TWO SUITES are a matched pair. `verify_features.js`
and `verify_badges.js` assert the new intent, so main's copies fail against a
round E artifact **by design**: `no two marks overlap anywhere` and `crowded
rings collapse to a counted seal` are the two rules this round replaces, and
main's fan test crashes on `.dataset` of undefined hunting for a ring a
neighbour collapsed. Those failures are the signal, not a problem.

```bash
git archive origin/main docs/prototypes | tar -x -C /tmp/pinned
cp docs/prototypes/qa/verify_{features,badges}.js /tmp/pinned/docs/prototypes/qa/
cd /tmp/pinned/docs/prototypes
GROUNDS_FILE="file:///.../ga-map/docs/prototypes/grounds-v0.html" node qa/verify_features.js
```

### The protocol was replicated, not just trusted

Round E was built by replaying `patch_e1` through `patch_e11` onto `origin/main`'s own
artifact in a clean worktree, because the shared tree's copy carried another lane's
unshipped publish round in the same file. The map lane replayed the SAME eleven scripts
on the SAME base, in a different worktree, at the same time, without coordinating on
anything but the script names:

```
theirs   sha256 86408222b7bf…   4751111 bytes
main     sha256 86408222b7bf…   4751111 bytes   IDENTICAL
```

And the served filename is content-hashed: production answers
`/grounds/grounds-86408222b7bf.html`. So the live map is provably the bytes those scripts
produce, established without trusting either operator. Two people, two worktrees, one
result.

Their gates also ran against an artifact rebuilt from scratch rather than the one these
two suites were developed alongside, which is the one thing a matched pair cannot prove
about itself.

**This is what the `newline=""` discipline is protecting.** Six scripts in this directory
read and wrote the artifact in text mode, which on Windows returns 5443660 bytes and a
different content hash for changing nothing at all (fixed in `a945c92`). One text-mode
writer anywhere in the chain and the two artifacts differ by every line, the hashes stop
matching the served filename, and the replication argument degrades to "they both looked
right".

**PIN BOTH SIDES OR NEITHER.** Pinning the artifact to a SHA and reading the
suite off the shared working tree cost a false bug report this round: a
`window.SCENE` term that existed only in another lane's uncommitted mid-edit
state was reported as a defect on main, where it has never existed. Half-pinning
looks rigorous, which is what makes it expensive. One command closes it:
`git show origin/main:<suite> | grep -c "<marker>"`.

Two more that came out of the same exchange:

- **Grep for the syntax that would EXECUTE, not for the name.** `window.SCENE`
  matched the docstring *explaining* the trap and nearly produced a second false
  alarm. `typeof window.SCENE\|window\.SCENE &&` cannot match prose. Comments
  here name the bugs they prevent, so this recurs as the comments improve.
- **Prove which file a gate read.** The export carries the artifact's version, so
  `map_scene.version == v0.8-roundE` is what makes a schema green provably about
  this round rather than about a stale file in the working directory.

## Gates

All green: `check_blocks`, `verify_doors`, `verify_features`, `verify_badges`,
`verify_loom`, `verify_skin_bridge`, `verify_vocab_bridge`, schema round-trip.

Three assertions in `verify_features.js` encoded the OLD intent and were
rewritten rather than relaxed, because "no two marks overlap anywhere" is a
rule this round deliberately removed:

- `no two marks overlap anywhere on the land` became **every mark stays on its
  own building's ring** (`reach` = the widest ring the layout can hand out) plus
  **two marks on one ring never touch**, which is the 44 px tap target and a
  correctness rule rather than a tidiness one.
- `every mark answers its own tap` now asks `nearestSeal()` instead of
  `elementFromPoint`, because stacking stopped being the mechanism.
- `crowded rings collapse to a counted seal` became its inverse, **no ring is
  collapsed by its neighbours**.

**Then the map lane caught that ONE CAMERA PROVES ONE CAMERA**, which is the
more important of their two catches. The thumb check ran at z 1.7, and that is
the easy end: `off` comes from `_crownOff`, which shrinks with the LOD scale, so
pulling back tightens every ring AND converges the buildings at once. Swept:

| z | ink | doors | unreliable | worst gap |
|---|---|---|---|---|
| 1.00 - 1.20 | 22 | 50 | **4 (8%)** | 12.3 px |
| 1.35 | 22 | 50 | 0 | 24.9 px |
| 1.45 - 1.60 | 28 | 50 | **3 (6%)** | 18.8 px |
| 1.70 - 2.00 | 28 | 50 | 0 | 28.3 px |

**No rotation budget clears the whole range**, and that is not a tuning failure.
Measured across (budget, step) tables from 18/3 to 42/3, the best clears only
from z 1.7 up. At z 1.0 there are 50 doors in a converging area and the screen
does not hold 50 exclusion zones. A zoom gate would hide 50 doors to fix 4, so
it was not taken.

The second band exists for a reason worth keeping: `.bmid` takes a seal from
22 px to 28 at z 1.45 while the ring geometry does not change, so **the ink
grows before the ring does**. Moving that boundary up is the cheap lever if the
budget ever needs to come down.

So the swept check is a RATCHET, like the brand refs: the top of the range must
stay perfect, the known shortfall is recorded rather than hidden, and anything
that makes it meaningfully worse fails.

  D2 A1: from z 1.7 up every door has room for a thumb (1.7:0 2:0)
  D2 A1: the crowded low-zoom bands stay within budget (worst z 1: 4 of 50, budget 4)

One assertion was ADDED, and it is the one a passing tap test hides:
**every mark has room for a thumb**, the minimum centre-to-centre distance
across DIFFERENT buildings, against the seal's own ink width. A tap test asks
whether a click at an exact centre resolves; this asks how much room a finger
has. If it ever fails, do NOT raise `MARK_FLOOR`. The solver is greedy and a
higher floor has measured WORSE (floor 28 reached 20.8 px on nine-degree
rotation steps, against 23.1 px for floor 22, because a ring that keeps hunting
past a good-enough rotation settles somewhere that costs a later ring more than
it gained). Re-run `qa/_probe_floor.js` and widen `RING_ROT` instead.

`verify_badges.js` fan test used to hunt for a ring a NEIGHBOUR had collapsed,
which no longer happens. It now MAKES an intrinsic cluster (shrink a building
carrying several kinds until its own ring stops fitting) and fans that, which
is deterministic and tests the feature on its own terms.
